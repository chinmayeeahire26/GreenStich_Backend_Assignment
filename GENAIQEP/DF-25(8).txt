In the meantime, here are the most common causes and fixes:

## Common causes
### 1) You’re parsing the wrong field
Depending on the API/provider, the generated text is often in:
- `choices[0].message.content` (chat-style)
- `choices[0].text` (older completions-style)
- `output_text` / `output[0].content[0].text` (varies by SDK)

If your code is doing something like `response.prompt` or `response.data.prompt`, it will fail.

### 2) You’re expecting the prompt to be echoed back
Many APIs do not return your original prompt unless you explicitly log it on your side. They return the model output and metadata, not the prompt.

### 3) You’re hitting a different endpoint/SDK shape than your code expects
For example, using a “responses” endpoint but parsing it like a “chat completions” response (or vice versa).

### 4) Error responses have a different schema
If the API returned an error, the body may look like:
- `{ "error": { "message": "...", ... } }`
and your code still tries to read the normal success fields.

## Quick debugging steps
- Log the entire JSON response before parsing.
- Check HTTP status code (200 vs 4xx/5xx).
- Confirm which endpoint you’re calling and match parsing logic to that schema.
